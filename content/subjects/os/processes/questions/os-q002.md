## Answer

In the simplified five-state model, new work is admitted to ready, dispatched to
running, and eventually terminates. Running work can become blocked while waiting
for an event, then return to ready when that event completes. Preemption can move
running work back to ready. Ready means able to run; blocked means unable to
proceed until an event occurs. Real operating systems have more detailed states
and commonly schedule threads rather than treating a multithreaded process as one
execution state.

### Supporting reasoning

| Transition | Typical cause |
| --- | --- |
| New → Ready | Creation/admission completes |
| Ready → Running | Scheduler dispatch |
| Running → Ready | Time slice expires or other preemption |
| Running → Blocked | Wait for I/O, a lock, or another event |
| Blocked → Ready | Required event completes |
| Running → Terminated | Exit or fatal termination |

I/O completion makes work runnable; it does not guarantee immediate CPU ownership.
A free CPU cannot make a still-blocked thread proceed without its required event.

### Qualifications

This model is not a literal exhaustive list of kernel states or transitions. OSes
may distinguish suspended, stopped, different sleep states, or exit/reaping states.
In a multithreaded process, one thread can be blocked while another is running.

### Follow-up prompts

- Why is ready different from blocked even when neither is executing?
- What information does a process/thread control structure need to resume execution?
- What happens between a device completing I/O and the waiting work running again?
- Can every thread in a process be described by one scheduling state?

### What a good answer covers

- Names the simplified states and explains their meanings.
- Connects transitions to dispatch, preemption, waiting, completion, and exit.
- Does not jump directly from blocked to running as a guaranteed transition.
- Identifies the model as an abstraction and distinguishes thread scheduling.
