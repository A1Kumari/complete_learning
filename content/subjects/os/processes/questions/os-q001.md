## Answer

A process provides an address space and OS-managed resources. A thread is an
execution path inside a process, with its own stack, registers, program counter,
and thread-local state. Threads normally share their process's memory and many
resources, so they often need less setup than independent processes. That sharing
makes communication convenient but requires synchronization and shares a failure
boundary. “Lightweight” is a useful comparison, not a universal performance guarantee.

### Supporting reasoning

Separate processes normally have isolated address spaces; explicit IPC or shared
memory can connect them. Threads already share code/heap mappings and many process
resources. “Own stack” does not mean inaccessible to other native threads if a
pointer is shared.

Protect a shared read-modify-write operation with a suitable lock or atomic
operation. Waiting for both threads to terminate does not repair lost updates.
A fatal native-memory error in one thread can terminate its entire process;
a caught language-level exception is not necessarily such an error.

### Qualifications

`fork()` commonly uses copy-on-write rather than eagerly copying every physical
page. Thread creation and context-switch costs depend on the OS, hardware, cache
state, and workload. Same-process thread switches can avoid some address-space
switching work, but do not promise zero TLB work or a fixed speed advantage.

Go goroutines are runtime-managed tasks scheduled across OS threads. The OS
schedules those threads; it does not see every Go program as a single thread.

### What a good answer covers

- Distinguishes resource/isolation ownership from execution state.
- Identifies shared memory and per-thread stack/register state.
- Allows explicit sharing between processes rather than saying they cannot share.
- Connects sharing to synchronization and failure trade-offs.
- Qualifies performance claims and separates runtime tasks from OS threads.
